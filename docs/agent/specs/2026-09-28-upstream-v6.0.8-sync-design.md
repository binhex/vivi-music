# Upstream v6.0.8 sync for the fork tree - design

- **Date:** 2026-09-28
- **Status:** approved for implementation
- **Scope:** repository hygiene, CI canary, documentation. **No product code change and no new release.**

## Problem

The fork ships upstream v6.0.8 already, but its own tree does not contain it:

| Observation | Evidence |
| --- | --- |
| Upstream v6.0.8 = upstream `main` HEAD = `206e7ae0`, published 2026-09-25 | `git fetch` by URL; tag and branch resolve to the same commit |
| The fork's base is upstream `6087580f` (2026-09-12, the v6.0.7 era) | `git merge-base HEAD upstream/main` |
| Upstream moved 33 files (+2141/-346) past that base | `git diff --stat 6087580f..206e7ae0` |
| The fork's tree no longer passes its own consistency check | `apply.sh --check` on the fork tree: `01` OK, **`02-recommendations.patch` fails at `HomeViewModel.kt:388`** |
| The same check passes against real upstream v6.0.8 | `apply.sh --check` in a detached `206e7ae0` worktree: `OK 01`, `OK 02`, **exit 0** |
| The released artifact is already v6.0.8-based | release `v6.0.8-local.1` came from CI run `36420571484` (**success**, 39m), artifacts `vivi-foss-debug-206e7ae` and `lint-foss-206e7ae` |

So the defect is not the shipped APK - it is that a clone of the fork can neither build what CI builds nor
answer "am I current?" without manual archaeology. Nothing warned about the lag for two weeks.

## Goal

Make the fork's tracked tree current with upstream v6.0.8 and self-consistent again, while preserving every
local patch, doc and workflow exactly as they are. Then make such a lag visible automatically.

## Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | Merge upstream v6.0.8 into the fork tree; **no new tag or release** | The artifact cannot change: CI builds *upstream main + `local-patches/**`*, and neither changes. A release would imply user-visible change that does not exist. |
| D2 | Add a permanent `upstream` remote with its push URL disabled | Makes the sync repeatable in-repo (`git fetch upstream && git merge upstream/main`) and lets `git diff upstream/main` answer "is the tree current?". Push is set to `no_push` so it can never reach upstream. |
| D3 | Restore upstream's stray root file `et --hard 33c82f9` | Local commit `453fd6cf` deleted it; that is the fork's only non-additive change. Restoring it makes the invariant *fork tree = upstream + our added files* true and verifiable in one command. |
| D4 | A real merge commit, not squash or rebase | Records upstream ancestry, so the next sync diffs only new upstream commits. Rebase would rewrite pushed history and invalidate the relationship the existing tags depend on. |
| D5 | Verification is local checks on the merged tree, no requested CI re-run | `local-build.yml` reads only `local-patches/**` plus upstream main, so a re-run would rebuild inputs already proven green in `36420571484`. |
| D6 | Update `local-patches/README.md` and add a tree-freshness canary that reports without failing | The documentation describes a separate-clone flow the repo cannot perform; the canary addresses the root cause (an unnoticed lag). |

## Design

### One-time setup

```bash
git remote add upstream https://github.com/vivizzz007/vivi-music.git
git remote set-url --push upstream no_push
git update-ref -d refs/remotes/upstream-v608/main        # exploration refs from the design step
git update-ref -d refs/remotes/upstream-v608/tag-v6.0.8
git fetch --no-tags upstream main                        # -> upstream/main == 206e7ae0 == v6.0.8
```

### Sync procedure

```bash
git merge --no-commit upstream/main
git checkout upstream/main -- 'et --hard 33c82f9'        # undo the only non-additive local change
git commit -m "local: sync upstream v6.0.8 (206e7ae0) into the fork tree"
```

- `--no-commit` is required: the stray-file deletion (base has the file, we deleted it, upstream left it
  alone) would otherwise survive the merge, leaving the tree non-additive.
- Folding the restore into the merge commit keeps every commit on `main` invariant-clean.
- Conflict policy: `git merge-tree --write-tree HEAD upstream/main` exits 0 today, so a conflict would mean
  an assumption broke. **Stop and report; do not hand-resolve.**
- Expected tree effects, all from upstream: `app/build.gradle.kts` versionCode 76 -> 77 and versionName
  `6.0.7` -> `6.0.8`; `gradle/libs.versions.toml` innertubex `v0.6.0` -> `v0.7.0`; the Library, lyrics and
  InnerTubeX changes; `.github/workflows/nightly-telegram.yml`; `Changelog/Stablemd/77.md`;
  `fastlane/metadata/android/en-US/changelogs/77.txt`.
- `local-patches/**`, `docs/agent/**` and the two fork workflows are untouched by the merge.
- Follow-up commits: `local(ci): report when the fork tree falls behind upstream`, then
  `local(docs): document the in-repo upstream sync`.
- Then `git push origin main`. No tag, no release, no branch deletion.

### CI canary - a second job in `.github/workflows/upstream-drift.yml`

```yaml
on:
  schedule:
    - cron: '0 6 * * 1'
  workflow_dispatch:
    inputs:
      fork_ref:
        description: Ref of this fork to compare with upstream main
        default: main

jobs:
  drift: ...            # unchanged: do the patches still apply to upstream main?

  freshness:
    name: Fork tree is current with upstream main
    runs-on: ubuntu-latest
    timeout-minutes: 10
    permissions:
      contents: read
      issues: write
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ inputs.fork_ref || 'main' }}   # depth 1 is enough: trees are compared, not history
      - name: Fetch upstream main
        run: |
          set -euo pipefail
          git remote add upstream https://github.com/vivizzz007/vivi-music.git
          git fetch --no-tags --depth=1 upstream main
      - name: Compare the trees
        id: tree
        run: |
          set -euo pipefail
          upstream_sha="$(git rev-parse --short upstream/main)"
          # NUL-delimited path lists: one byte per path, so a name containing a newline cannot be
          # miscounted the way a line-based grep count would.
          git diff --name-only -z --no-renames --diff-filter=DMTUXB upstream/main HEAD >"${RUNNER_TEMP}/tree-nonadditive.z"
          git diff --name-only -z --no-renames --diff-filter=A upstream/main HEAD >"${RUNNER_TEMP}/tree-added.z"
          nonadditive="$(tr -cd '\0' <"${RUNNER_TEMP}/tree-nonadditive.z" | wc -c)"
          # Additions are checked against the paths this repo owns, because an upstream file that upstream
          # deleted while this tree still carries it also appears as an addition.
          unexpected=0
          while IFS= read -r -d '' added; do
            case "${added}" in
              local-patches/*|docs/agent/*) ;;
              .github/workflows/local-build.yml|.github/workflows/upstream-drift.yml) ;;
              *) unexpected=$((unexpected + 1)) ;;
            esac
          done <"${RUNNER_TEMP}/tree-added.z"
          offending="$((nonadditive + unexpected))"
```

- **Detection rule:** the invariant is "fork tree = upstream main + the files this repo owns", so the
  only permitted difference is an addition under `local-patches/**`, `docs/agent/**` or one of the two
  fork workflows. Non-additions (`M`, `D`, `T`, `U`, `X`, `B`) come from `--diff-filter=DMTUXB`; additions
  are then matched against those owned paths. Two adversarial cases drove this shape: a line-based
  `grep -cvE '^A'` miscounts a filename containing a newline, and an upstream file that upstream deleted
  while this tree still carries it shows as an `A`, which a pure "everything must be an addition" test
  would wave through as a clean tree and would even use to close an open lag issue. One NUL byte per path
  fixes the first; the owned-path allowlist fixes the second. `--no-renames` keeps the states unambiguous,
  and a depth-1 fetch is sufficient because only trees are compared.
- **Reporting:** a `GITHUB_STEP_SUMMARY` block that shows both lists (the changed or deleted upstream files,
  and the additions outside the owned paths) so a count never arrives without the paths that made it, a
  `::warning::` annotation whose `fork_ref` is reduced to `A-Za-z0-9._/-` so a newline decoded from `%0A`
  cannot start a second workflow command, and, **when the repository has Issues enabled**, a deduplicated
  issue titled `Fork tree is behind upstream main` - created when absent, commented when open, closed when
  the tree is clean. The issue channel is opportunistic: the job asks `gh api
  repos/$GITHUB_REPOSITORY --jq .has_issues` once, treats an API failure as `unknown` (still summary-only,
  but with a `::notice::` breadcrumb and a summary line that says the setting could not be read, rather than
  a silent `false`), skips the issue calls unless the answer is `true`, and treats any issue-call failure as
  another warning, so the job never fails. This matters because `binhex/vivi-music` currently has Issues
  switched off, where `gh issue list` exits 1 and, under `set -euo pipefail`, would otherwise fail both the
  lag and the clean path. Deduplication matches the title from `gh issue list --limit 100 --json
  number,title` rather than the search index, and the job takes a `concurrency` group, so a dispatch cannot
  race a scheduled run into creating a duplicate issue.
- **Untrusted input:** `fork_ref` reaches the shell through `env:` (`FORK_REF`) and is then quoted, rather
  than being text-substituted into the script, so a crafted ref cannot inject commands; it is only ever
  used as data.
- **Fail loud where it matters:** if the diff files cannot be produced, the `Compare the trees` step exits
  non-zero instead of reporting a silent `0`. The never-fatal contract is about lags and issue reporting,
  not about hiding a broken filesystem. The summary's own display pipelines use `sed -n '1,20p'`, which
  reads to EOF, so no writer can take SIGPIPE (the failure mode that would have broken the contract).
- **Both jobs are serialised:** `drift` and `freshness` each take their own `concurrency` group
  (`upstream-drift-drift`, `upstream-drift-freshness`) with `cancel-in-progress: false`, so overlapping
  scheduled and manual runs queue instead of racing each other's issue lookups.
- **Deliberately omitted:** "behind by how many commits". That needs ancestry, which a depth-1 fetch
  cannot answer reliably, and file differences are the actionable number.
- The `fork_ref` input exists so the lag path is provable on demand, not only when a real lag occurs.

### Documentation

`local-patches/README.md`:

- `## Updating for a new upstream release` is rewritten around the in-repo flow: one-time remote setup,
  `git fetch` + `git merge --no-commit`, then the two health checks
  (`local-patches/apply.sh --check` must print `OK` for every patch, and
  `git diff --name-only --diff-filter=DMTUXB upstream/main HEAD` must print nothing;
  `local-patches/apply.sh --check` must print `OK` for every patch).
- The existing separate-clone rebase procedure stays, as a sub-section used only when
  `apply.sh --check` fails.
- The weekly-check paragraph gains the freshness report and the explanation that a lag does not affect
  built APKs, because Local Patch Build compiles upstream main plus these patches - which is exactly why
  a lag can hide.
- `## Notes` gains one line: upstream carries the stray root file `et --hard 33c82f9` (committed there in
  June 2026); the fork keeps it so its tree stays upstream-plus-additions, which the canary depends on.

## Verification

1. `git diff --name-status --no-renames upstream/main HEAD | grep -cE '^[^A]'` -> `0`.
2. `local-patches/apply.sh --check` -> exit 0 (fails today at `HomeViewModel.kt:388`).
3. `pytest local-patches/tests` -> 47 passed; `local-patches/tests/test-signing-key-stability.sh` ->
   16 passed, 0 failed, 0 pending.
4. `markdownlint` on the changed README -> 0 non-MD013 findings, no prose line over 120 characters.
5. `Upstream Drift Check` dispatched twice: `fork_ref=v6.0.7-local.8` must report the lag (step summary plus
   warning annotation, and the deduplicated issue when the repository has Issues enabled) while finishing
   green; `fork_ref=main` must report clean and close any lag issue, green. With Issues disabled - the
   current state of `binhex/vivi-music` - the lag appears in the summary only, and the run must still be
   green on both paths.
6. `git status` clean; no `.rej`/`.orig` files; no extra `git worktree` entries.
7. The Local Patch Build auto-triggered by the README push is reported as an extra signal, not as the bar.

Kotlin compile, unit tests and Kover stay in CI. That is defensible here because check 1 proves the merged
`app/` tree is byte-identical to upstream v6.0.8, and run `36420571484` already compiled and unit-tested
exactly that source plus these patches. This sync introduces no new Kotlin.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Merge conflict | None expected (`merge-tree` exit 0). If one appears, stop and report; do not hand-resolve. |
| A typo in the new workflow hides until Monday | The two dispatches are part of the verification bar, not optional. |
| Issue noise from the canary | Deduplicated by title; closed automatically when the tree is current. |
| Runner time | One automatic Local Patch Build (~40 min) from the README path filter; the dispatches take minutes. |

## Rollback

Every change is an ordinary commit on a branch that is never rewritten. `git revert -m 1 <sync-merge>`
restores the pre-sync tree (it would re-delete the stray file and trip the canary, which is honest); the CI
and docs commits revert independently. No tag or release moves, so nothing user-installable is affected.
`git remote remove upstream` undoes the one-time setup.

## Out of scope

- Any new tag or release; any change to the `v6.0.8-local.1` tag or its artifacts.
- Regenerating `local-patches/01-*.patch` or `02-*.patch`: both already apply cleanly to v6.0.8.
- Rebasing, force-pushing or any history rewrite.
- Pulling upstream commits beyond v6.0.8.
- Building locally with an Android toolchain on this host (Java 11, no Gradle, no Android SDK).

## Named residuals

- The freshness canary's issue branch is exercised only when the repository has Issues enabled. Since
  `binhex/vivi-music` has them switched off, that branch is covered by a local simulation of the guarded
  scripts (both paths exit 0, including the worst case where `has_issues` reports true and the issue call
  itself refuses) rather than by the CI dispatch, which exercises the summary-only path.
- `local-patches/README.md` lives under the `local-patches/**` path filter, so editing it starts a Local
  Patch Build. Suppressing that would mean editing `local-build.yml`, which would itself start a build;
  left as is.
- Both jobs keep at most one pending run per concurrency group, and GitHub cancels an older *pending* run
  when a newer one queues: two dispatches in quick succession can drop a queued weekly run. The running
  canary is never cancelled.
- The allowlist assumes upstream owns none of the owned prefixes. If upstream ever adds a file under
  `local-patches/**`, `docs/agent/**` or one of the two workflow names and later deletes it, that path
  arrives as an allowlisted addition. Unreachable today; worth revisiting if upstream ever writes into
  those prefixes.
- The README's manual health check is a one-liner, so a rename *inside* an owned prefix passes its `grep`
  filter although the workflow counts the deleted side. The workflow is the authoritative check.
- The canary answers "is the tree current", not "are the patches still correct" - the existing `drift` job
  owns that question.
- With Issues disabled (this fork's state) a lag reaches nobody by itself: it appears in the run summary
  and as a warning annotation, and successful runs notify no one. The alternative - failing the run on a
  lag - was rejected by design, because the built APK is unaffected by a lag.
- Both jobs hard-code the upstream coordinates (`github.com/vivizzz007/vivi-music`, branch `main`) and the
  fork's own default branch; a rename or a moved default branch needs an edit to `upstream-drift.yml`.
- The pre-existing `drift` job's report step now survives a repository with Issues disabled (`|| true` on
  its issue lookup plus warnings on the issue calls), so a real patch drift still writes its summary and
  still fails the run through the job's final step. Its own issue lookup keeps the pre-existing
  search-index form; only the freshness job moved to title matching.
- A scheduled run of this workflow is known to fire in this fork: run `36423846470` was `event: schedule`
  and completed, so the "forks do not run schedules until enabled" caveat does not apply here.
